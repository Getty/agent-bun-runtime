# Getty integration contract

Contract version 1 (`gettyBun.contractVersion`), implemented by agent-bun-runtime 0.1.0 and, with the optional additions marked "from 0.2.0" (ADR 0011), by 0.2.0. These are Getty design decisions, recorded in the `agent-bun-runtime` repository (`docs/plan.md`, `docs/adr/0001`–`0011`); where this skill and they disagree at the release tag, they win.

- **Starters** (`bootstrap/getty-bun.sh`, `bootstrap/getty-bun.ps1`, from 0.2.0 the polyglot `bootstrap/getty-bun.cmd`, the version table and the pin render): `bootstrap/README.md` is their behavior contract. Phase 1 gate: CI 45603412444 (pull request) and 45604685681 (`main`) at `262bc95`, 10 of 10 jobs green ([verification.md](verification.md), "Provider gate"). In this skill, "executed, scenario N" means that suite in run 45603412444, on all legs the scenario runs on. Later changes (k29: Bun starts without the project's configuration; the 0.2.0 additions) are checked by the release's CI. For the 0.2.0 additions, "executed locally" means the suite under `GETTY_BUN_TEST_STARTER=sh` on linux-x64 (dash 0.5.12, Bun 1.4.5) before the release's CI ran; their macOS and Windows legs are pending until it has.
- **Delivery:** the skilletor template `getty-bun-install` in the release's `skills/`.
- **SDK** `@getty/agent-bun-runtime` with the codecs for Codex and Claude Code ([sdk.md](sdk.md)).
- **Not checked:** how Codex and Claude Code run the starters and the codecs; the CI runners are no desktops, and no real host has run a codec from agent-bun-runtime.

## Responsibilities

| Component | Owns |
| --- | --- |
| Bootstrap (`agent-bun-runtime` `bootstrap/`; delivered as template `getty-bun-install`) | Reviewed version table (SHA256 per target, expected archive member), pin render, the two starters: target detection, install on demand under the OS lock, staging, receipt, atomic publish, fast path, `run`, `ensure`, `status`. |
| SDK `@getty/agent-bun-runtime` | Invocation envelope, the Codex and Claude Code codecs, effects, `main(): Promise<number>`, exit codes. Never installs, downloads, or edits lockfiles, not even in a diagnostic command. |
| Consumer plugin/tool | `gettyBun` pin in `package.json`, `vars.bun_version` for the template, the starters copied from the rendered template and committed, the committed bundled entry built on the SDK, CI that checks both, host hook files, setup skill for repair and diagnosis, hook timeouts above the lock wait plus one download. |
| Agent host | Instruction/skill/hook surfaces, workspace trust, hook review, execution, timeouts. |
| Setup agent | Repair and diagnosis through the packaged setup skill within session authorization; reporting what the starter said. Not the install path. |

Call the provider `getty-bun`; its repository is `agent-bun-runtime`. There is no `getty-bun` command on PATH: the provider is the pair of rendered starters committed into each consumer. Keep the managed executable named `bun` or `bun.exe`. The starter interface is `run`, `ensure`, `status` and, from 0.2.0, `run-ready`, nothing else; `repair`, `gc`, upgrade and rollback are later and unspecified. Missing provider behavior (a target, a starter feature, an event or effect) is built in `agent-bun-runtime` first, never worked around in the consumer.

## Starter interface

```text
getty-bun.sh  run <entry> [args...]        ensure, then exec the absolute Bun (flags below)
getty-bun.sh  run-ready <entry> [args...]  run when the slot is ready; never installs (from 0.2.0)
getty-bun.sh  ensure                       install if missing; nothing on stdout
getty-bun.sh  status                       one JSON object on stdout: pin, target, slot, state
getty-bun.ps1 <same commands>              identical behavior and exit codes
getty-bun.cmd <same commands>              polyglot for Claude Code shell-form hooks (from 0.2.0)
```

Plan, "Starter interface"; details in agent-bun-runtime `bootstrap/README.md`. Executed unless marked otherwise.

- **Location.** A consumer carries the starters as `<consumer-root>/bootstrap/getty-bun.sh` and `<consumer-root>/bootstrap/getty-bun.ps1`, and from 0.2.0 the polyglot `getty-bun.cmd` beside them when it serves Claude Code on Windows; the consumer root is the parent of the starter's directory, never the working directory. `<entry>` is relative to that root, written with `/` (the PowerShell starter converts it).
- **Install on demand.** `run` and `ensure` take the fast path for a matching slot and install a missing one under the OS lock; concurrent calls wait on the same lock, bounded, then re-check (scenarios 1, 2, 3).
- **Targets and the x64 slot choice.** Linux `linux-x64`, `linux-x64-baseline`, `linux-aarch64`; from 0.2.0 macOS `darwin-x64` and `darwin-aarch64` (a Rosetta 2 shell on Apple silicon takes `darwin-aarch64`; no `darwin-x64-baseline`, since every Mac that runs Bun 1.4.5's minimum macOS 13 has AVX2); Windows `windows-x64`, `windows-x64-baseline`. On x64 both starters take the first slot that exists of `<os>-x64`, then `<os>-x64-baseline`, and detect the CPU only when neither exists (`getty-bun.sh` from 0.2.0, `getty-bun.ps1` since 0.1.0): `ready` runs it, `mismatch` fails closed, and a mismatching `-x64` slot is never skipped for a ready baseline one. (Slot choice: executed locally, `bootstrap/test/fast-target.test.ts`. macOS: the mapping and Rosetta rule source-checked and covered by the pure test `bootstrap/test/targets.test.ts`; no Mac has run the starter yet, CI macOS legs pending. Details: `bootstrap/README.md`, "POSIX starter: targets, `run-ready`, download".)
- **`status` never installs.** It prints `pin`, `target`, `slot` (absolute) and `state`, one of `ready`, `missing`, `mismatch` and, from 0.2.0, `undeclared` (the platform is not in the pin's platforms line; `target` and `slot` are then `null`, see "Canonical consumer requirement"), and exits 0 whenever it printed the object, 1 when the state cannot be determined (for example an unsupported target, or an invalid `GETTY_HOME` or `GETTY_BUN_LOCK_WAIT`).
- **`run-ready` (from 0.2.0).** For a hook that must never wait for an install: a `ready` slot runs exactly as `run`; a `missing` one exits 0 with nothing on stdout and one stderr line `getty-bun: Bun <version> <target> is not installed yet (<slot>); run-ready skipped <entry>` (`getty-bun.ps1` detects no CPU there, since `Add-Type` would compile on every such hook, and names the first candidate, `windows-x64`), and takes no lock, stages nothing and downloads nothing; `mismatch`, an invalid environment or an unsupported target fail as `run` does. Use it on hot hooks with a short timeout, such as a `PreToolUse` guard with a 5 s budget (loadguard's), while a `SessionStart` hook with timeout 600 calls `ensure` or `run` and does the install; until that has finished, the hot hook stays silent instead of running into its timeout. (Executed locally, `bootstrap/test/run-ready.test.ts`; `getty-bun.ps1`: a local run with pwsh 7.7.0 on Linux, Windows legs pending.)
- **Download, resume, no orphan (from 0.2.0).** The archive downloads under the install lock to `<GETTY_HOME>/runtimes/bun/.downloads/<version>/<target>/<archive>.part`. An interrupted install (signal, kill, timeout, network error) keeps the `.part`, and the next install resumes it with an HTTP range; a server that ignores the range starts the file over; a checksum mismatch deletes the `.part` before the failure; a verified archive moves into staging, so a published install leaves the directory empty. A starter killed with SIGKILL leaves no download process running: `getty-bun.sh` runs `curl`/`wget` beside a watchdog that stops it within about a second once the starter is gone (limit: a killed starter that its parent has not reaped yet still counts as alive); `getty-bun.ps1` downloads in process and has no child to orphan. (POSIX: executed locally, `bootstrap/test/resume.test.ts`, and with curl 8.14.1 and GNU Wget 1.25.0 in the runs `bootstrap/README.md` records; `getty-bun.ps1`: a local run with pwsh 7.7.0 on Linux against a range server, Windows legs pending.)
- **Lock released before Bun.** `getty-bun.sh` holds the lock on a descriptor that only the install's command group has open; `getty-bun.ps1` disposes the lock stream after publishing; an entry never holds it. The rule rests on flock(2)/execve(2) semantics ([installation-locking.md](installation-locking.md), step 6); executed (scenario 2b: while an entry runs after a fresh install, the test takes the lock without waiting). macOS ships no `flock(1)`, so there `getty-bun.sh` (from 0.2.0) takes the same `flock(2)` lock on fd 9 through the system `perl`, polling with `LOCK_NB` until `GETTY_BUN_LOCK_WAIT` runs out ([installation-locking.md](installation-locking.md); executed only on Linux, in a copy of the starter forced onto the perl lock, perl 5.40.1: timeout, three parallel `run`s sharing one download, mutual exclusion with `flock(1)` both ways; on macOS not checked, CI macOS legs pending).
- **Bun without the project.** `run` starts `<slot>/bin/bun --no-install --config=<empty file> --no-env-file <root>/<entry> [args...]` with `BUN_OPTIONS`, `BUN_INSPECT_PRELOAD`, `BUN_INSPECT`, `BUN_INSPECT_CONNECT_TO`, `NODE_PATH`, `NODE_COMPILE_CACHE` and `BUN_INTERNAL_WEBVIEW_HOST` removed from Bun's environment and `BUN_RUNTIME_TRANSPILER_CACHE_PATH` set to `0` (`BUN_OPTIONS` adds flags such as `--preload` past `--config`; the others add a preload, start the debugger, resolve modules outside the plugin, pick a code cache directory, or on macOS replace the entry with a webview host). The transpiler cache variable is set, not removed, from 0.2.0 (k46): removed, Bun would pick its default cache directory and write a `.pile` per transpiled non-bundled entry into the user's cache; `0` turns that cache off, and a `--target=bun` bundle is not cached either way (executed on Bun 1.4.5 linux-x64 with `getty-bun.sh`; `getty-bun.ps1`: a local run with pwsh 7.7.0 on Linux, Windows legs pending). The run keeps the hook's working directory (the SDK's `location.processCwd`). The empty file is `/dev/null` for `getty-bun.sh` and `<GETTY_HOME>\runtimes\bun\.config\bunfig.toml`, created by `run` and `ensure`, for `getty-bun.ps1`; a missing `--config` file would make Bun exit 1. So the project's `bunfig.toml` (preload, `[define]`), `.env`, `.env.local`, `.env.<NODE_ENV>`, a `BUN_OPTIONS` preload and those variables never reach the entry (`bootstrap/README.md`, "Starting Bun: no project configuration"; executed on Bun 1.4.5 linux-x64, cards k29 and k40: the removal of every variable is tested; the preload, `NODE_PATH` and the cache writes are executed in the suite's controls, the debugger effect only in a raw probe outside the suite, while "restored as code" and the macOS webview host are source-checked; a `BUN_INSPECT` value with `?wait=1` would hold a hook until the host's timeout, as that probe showed; the Windows legs in the release's CI). The cleanup applies to the whole process tree below the starter, not only to Bun: a tool the entry starts (`node`, `npm`, another Bun) inherits the cleaned environment, so it loses the user's `NODE_PATH` and `NODE_COMPILE_CACHE`, and debugging an entry with `BUN_INSPECT` through the starter no longer works (run the slot's Bun by hand for that) (k47). Kept, since they load no code: `NODE_OPTIONS` (Bun ignores it), `XDG_CACHE_HOME`, `HOME`, `NODE_CHANNEL_FD`, and (k48) `NODE_DISABLE_COMPILE_CACHE`, `NODE_COMPILE_CACHE_PORTABLE` and `BUN_JSC_*`; the first two only switch off or re-key a compile cache that, without `NODE_COMPILE_CACHE`, only the entry itself can turn on, and `BUN_JSC_*` sets JavaScriptCore engine options (JIT, GC, profiling), where an unknown name makes Bun exit 1 before the entry runs (source and probes: `bootstrap/README.md`, "Starting Bun: no project configuration"). A Bun child process the entry starts inherits that cwd and environment and needs the same flags ([dependencies-and-execution.md](dependencies-and-execution.md)).
- **Streams.** stdout belongs to the entry (hook JSON); starter messages go to stderr, also during an install inside `run` (scenario 8). Give hook input on a pipe; for a stdin that is a character device under Git Bash, see [paths-platforms.md](paths-platforms.md) (a hint, not a requirement).
- **Exit codes.** Exit 0 when ready; 1 for every starter failure, with one stderr line beginning `getty-bun: ` that names what failed and where. The starter never exits 2 for its own failures (some hosts read 2 as a block); the entry's exit code passes through unchanged, 2 included (scenario 8: 0, 1, 2, 7, 42). 2 stays the entry's (ADR 0007, superseding that part of ADR 0002); an SDK entry returns it only with `onFailure: "closed"` ([sdk.md](sdk.md)).
- **Exit codes on Windows are 0–255.** Bun 1.4.5 on Windows itself exits with the low byte of the entry's code (`process.exit(256)` gives 0), and the starters pass on what Bun exits with (executed, agent-bun-runtime CI 45589361806 and 45597390051). Keep an entry's codes within 0–255.
- **Entry arguments pass through unchanged (from 0.2.0).** Any argument after `<entry>`, those beginning with `-` included (`-x`, `-x:foo`, `-x:`, `--`, `--%`, `-File`, `-Command`; a lone `-` on POSIX), reaches the entry byte for byte through both starters, the Git Bash forwarding and the polyglot, except the few that fail on Windows (below). The empty string does too, except where a PowerShell session writes the native call: Windows PowerShell 5.1 drops an empty argument from any native command line, and pwsh 7.3 and later from a `.cmd` call (legacy passing for `.cmd` and `.bat`), so an empty argument is lost in the polyglot's hook line under PowerShell and in a Codex `commandWindows` line run by a Windows PowerShell 5.1 session (documented for PowerShell, `about_Preference_Variables`, `PSNativeCommandArgumentPassing`; for the starter derived, not checked; `bootstrap/README.md`, "Entry arguments"). The 0.1.0 rule "entry arguments never begin with `-`" is withdrawn (ADR 0011, item 5). **Not on Windows:** `-File` turns an argument after the script path that begins with `-` into a parameter, and binding can fail on one before `getty-bun.ps1` runs, with PowerShell's own message ("argument "name" is not valid") and exit 1, not a `getty-bun: ` line. So on Windows pass no lone `-` (Windows PowerShell 5.1 called directly rejected it, pwsh 7 called directly passed it: executed, agent-bun-runtime CI 46027293350 and 46031834399) and no argument that begins with `-:` (version-dependent: `-:foo` passed 5.1 called directly and was rejected by pwsh 7 called directly: executed, CI 46031834399); through the Git Bash forwarding and the polyglot the outcome per token is not determined; a dash followed by nothing but blanks fails too (source-checked only, PowerShell v6.0.0 and master `CommandLineParameterParser.cs`). Through the polyglot from a PowerShell hook shell (Windows PowerShell 5.1 and pwsh 7) also pass no `--%` and no argument that begins with `-` and contains a blank: `'--%'` did not reach the entry and `'-Command x'` arrived as `-Command` and `x`, while Git Bash as the hook shell passed the same list unchanged (executed, CI 46031834399; `cmd.exe` running the `.cmd` was checked there for stdin, stdout and exit code only; where PowerShell loses them: not checked). `-x`, `-x:foo`, `-x:`, `--`, `-File`, `-Command` and, outside that polyglot case, `--%` are not affected. `getty-bun.sh` passes `"$@"`. `getty-bun.ps1` reads its arguments from its process's own argument vector (`[Environment]::GetCommandLineArgs()`), after the host's `-File <script>`, which PowerShell's parameter binding does not touch; started any other way (`&` inside another PowerShell session, pwsh's positional script without `-File`) it falls back to `$args`, which that binding has re-parsed (pwsh 7 splits `-x:foo`, drops `--%`). Every way this contract names (Codex `commandWindows` with `-File`, the forwarding, the polyglot) uses `-File`. One exception comes from Bun itself: a lone `--` as the **first** entry argument is consumed by Bun 1.4.5, so `bun <entry> --` gives the entry no arguments while `bun <entry> x --` keeps it; the starters cannot change that, so do not make `--` an entry's first argument. In a hook line the shell parses the arguments first: in the polyglot line (`getty-bun-install`, section 3) write only words that mean the same to `sh` and PowerShell, single-quote the rest, leave `--%` out (unquoted it is PowerShell's stop-parsing token and never reaches the call; quoted, a PowerShell hook shell still lost it, above), and keep `&`, `|`, `<`, `>`, `^` and `%` out, since on Windows `cmd.exe` reads the arguments as PowerShell writes them onto its command line (not checked). (`getty-bun.sh` and the polyglot under dash, bash, BusyBox sh and zsh: executed locally, `bootstrap/test/entry-args.test.ts` and `bootstrap/test/polyglot.test.ts`, which also hold the raw Bun control for `--`. `getty-bun.ps1`, the Git Bash forwarding and the polyglot on Windows: executed, CI 46031834399, Windows PowerShell 5.1 and pwsh 7 legs, `bootstrap/test/entry-args.test.ts` and `bootstrap/test/polyglot.test.ts`, with the exceptions above.)
- **Fast path.** No network, no hashing, no CPU detection while an x64 slot exists (above), and Bun is not started: the receipt's first three lines name the pinned version and the target, and `bin/bun` (`bin\bun.exe`) is a non-empty regular file (executable on POSIX). Only the install compares `bun --version` with the pin, before publishing (plan, scenario 6; `getty-bun.ps1` also after publishing, see the open difference below). A slot that does not match fails closed with a message naming its path and is never overwritten (scenario 6). A damaged but non-empty executable therefore passes the fast path, and `run` ends with what the OS makes of it, not a `getty-bun: ` line; removing the slot directory lets the next call install it again (`bootstrap/README.md`, "Limit: a damaged executable").
- **Open difference from "identical behavior" (card `agent-bun-runtime k19`).** After publishing and releasing the lock, `getty-bun.ps1` runs `bun --version` on the published `bun.exe` once more and exits 1 if it does not run; the slot stays published, so the next call takes the fast path and the failure shows only once. `getty-bun.sh` has no such probe (source-checked, `getty-bun.ps1:566-572`). agent-bun-runtime decides on `k19` whether to drop it or specify it for both starters.

## Long-lived stdio server

From 0.2.0 the contract has a second entry kind beside the command hook (ADR 0011, item 9): a long-lived stdio server, as an MCP server is, started through `run` like a hook entry (`sh <root>/bootstrap/getty-bun.sh run dist/server.js`). Contract version 1 covers it unchanged.

- **Lifetime.** The entry runs until end of input on stdin or a signal, then exits with its own code. Through `getty-bun.sh`, Bun replaces the starter by `exec`: the host's process is Bun under the same PID, so the host's signals and the end of its pipes reach the entry directly, with no starter in between.
- **Streams.** stdout carries only the server's protocol, also during the first install inside `run`: every starter message goes to stderr. Request and response lines pass in both directions as the entry reads and writes them.
- **Same isolation.** The flags and the variable cleanup of "Bun without the project" apply unchanged.
- **Exit codes** 0–255 pass through unchanged, as for a hook.
- **First start.** No starter call on `SessionEnd` (or Codex `Interrupt`). A consumer whose MCP server runs through the starter adds a `SessionStart` command hook `ensure` with `timeout` 600, so the first MCP start normally finds a ready slot instead of installing inside the host's MCP start timeout. If a first start still installs and the host aborts it, the resume rule above keeps the partial download, and the next start continues it.
- **No SDK dependency** until the SDK has MCP (phase 5); the server entry is the consumer's own code, bundled like a hook entry.
- **Windows.** Only the stream behavior holds (lines, end of input, exit code): `getty-bun.ps1` starts Bun as a child, so there is no `exec`, no POSIX signal, and a host that kills PowerShell does not reach Bun, which keeps running (`k13`, the job object, is not in 0.2.0). The polyglot `getty-bun.cmd` does not start MCP servers: MCP has no shell form (ADR 0010).

Scenario: `bootstrap/test/stdio-server.test.ts`. It checks, through the starter, several request and response lines in a row with non-ASCII text, end of input reaching the entry, which answers and exits with its own code, the entry's PID being the one the test started (`exec`), a first install from the fixture mirror putting nothing but the entry's bytes on stdout, and SIGINT, SIGTERM and SIGHUP each reaching the entry, whose own exit code comes back. (Executed locally with `getty-bun.sh` under dash 0.5.12 on linux-x64, Bun 1.4.5; the Windows legs run the stream tests only and skip the PID and signal tests with that reason; Windows and macOS: pending until the release's CI ran. No real host has started a server through the starter.)

## Canonical consumer requirement

Place this custom object in the consumer's real `package.json`:

```json
{
  "gettyBun": {
    "contractVersion": 1,
    "bunVersion": "1.4.5"
  }
}
```

The version is the pin of the agent-bun-runtime release you build against (`bootstrap/versions.json` at its tag; 1.4.5 for 0.1.0, confirmed by Getty on 2026-11-25); this example is no compatibility certification. Contract version 1 accepts only stable `major.minor.patch`, without a leading `v`, ranges, tags, prereleases, or build suffixes.

[The schema](../assets/requirement.schema.json) validates the `gettyBun` object, not the entire manifest. Bun does not enforce it, and the starter does not read it: the starter's rendered pin block is the only thing that selects a version. The consumer's CI validates the `gettyBun` object against the schema, which rejects any `contractVersion` other than 1 and a malformed `bunVersion`, and checks that the pin block equals `gettyBun.bunVersion`.

`gettyBun.platforms` (optional, from 0.2.0) declares where the consumer runs: a list of unique values from `linux`, `darwin` and `windows`, at least one; without it, every platform. The starter does not read it either: the consumer renders the same list as `vars.bun_platforms` into one `# platforms` line of the pin block, and the starter reads that line. The consumer's CI checks that the line and `gettyBun.platforms` agree, as it checks the version. On a platform the line does not list, `run`, `run-ready` and `ensure` exit 0 with nothing on stdout and one `getty-bun: ` line on stderr, and install nothing; `status` reports the state `undeclared`. The usage, `GETTY_HOME`, `GETTY_BUN_LOCK_WAIT` and pin checks run before the platforms line in both starters, so an invalid `GETTY_HOME` or `GETTY_BUN_LOCK_WAIT` still exits 1 with its `getty-bun: ` line on an undeclared platform (source-checked, `getty-bun.sh` and `getty-bun.ps1`).

Keep ordinary requirements in `dependencies`/`devDependencies` and commit `bun.lock`; with a bundled entry they are build inputs resolved in CI, not on user machines. Do not infer the runtime pin from an arbitrary executable, `engines`, or a lockfile format. Optional toolchain metadata may mirror the exact pin but must not introduce a second runtime provisioner; see [prior-art.md](prior-art.md).

## Delivery of the starters

- **Pin block and render.** agent-bun-runtime `bootstrap/README.md` ("Pin block", "Render CLI") fixes both. The block is `#` lines between two marker lines, byte-identical in both starters: the `version` line, the optional `platforms` line (from 0.2.0, only when the consumer declares `gettyBun.platforms`), then one `target` line per target with archive name, SHA256 and the one archive member; seven targets from 0.2.0, five in 0.1.0. The polyglot `getty-bun.cmd` carries no pin block.
- **Template `getty-bun-install`.** The release's `skills/getty-bun-install/` holds both starters as templates with the version table of that release embedded, and from 0.2.0 `getty-bun.cmd` as a plain file, which skilletor copies byte for byte. A consumer installs it with skilletor from `Getty/agent-bun-runtime` at the release tag (`"ref": "v0.2.0"`, `"path": "skills"`) and sets `vars.bun_version`, and `vars.bun_platforms` when it declares `gettyBun.platforms`; a missing or unknown version, or a platforms value that is not a list of unique `linux`, `darwin`, `windows`, fails the render. skilletor renders only into the skill's own directory, so the consumer **copies** the rendered starters (and the polyglot, when it serves Claude Code on Windows) into its `bootstrap/` and commits them, because hosts install plugins by cloning.
- **CI check in the consumer.** The committed copies equal a fresh render (the polyglot included, where committed), the `# version` line equals `gettyBun.bunVersion`, and the `# platforms` line equals `gettyBun.platforms`, absent when that is not declared (the commands are in skill `getty-bun-install`, "Check the copy in CI").
- A new Bun version is a change in agent-bun-runtime (table plus tests; `bootstrap/README.md`, "Adding a version") and a release, then one `ref` and `vars.bun_version` bump per consumer.

## Shared immutable runtime slots

`runtimeRoot` is `<GETTY_HOME>/runtimes`, resolved once per user and execution environment ([paths-platforms.md](paths-platforms.md)).

| Item | Path relative to `runtimeRoot` |
| --- | --- |
| Runtime slot | `bun/<version>/<target>/` |
| Executable | `bun/<version>/<target>/bin/bun` or `bin/bun.exe` |
| Verified receipt | `bun/<version>/<target>/receipt.json` |
| Permanent mutex | `bun/.locks/<version>/<target>/.install.lock` |
| Attempt status | `bun/.locks/<version>/<target>/.installing` |
| Attempt stage | `bun/.staging/<unique-attempt-id>/` (same filesystem as the slots) |

The runtime key is the exact version plus a target from the reviewed table. Targets: `linux-x64`, `linux-x64-baseline`, `linux-aarch64`, `windows-x64`, `windows-x64-baseline`, and from 0.2.0 `darwin-x64`, `darwin-aarch64`; musl and `windows-aarch64` come later as explicit entries. Validate targets against the table before using them as path components; never accept arbitrary path fragments.

All consumers in that environment requesting the same key reuse one slot. Different versions coexist. Published executables and receipts are immutable: publish once by one atomic rename of the whole staged slot, receipt included; never overwrite or repair in place. A version change installs a new key beside the old one on the first starter call after the consumer update.

Keep the store outside consumer caches and data that clients may erase on plugin upgrade/uninstall. Consumers must not delete shared runtimes on removal. Sharing is per user/execution environment, not across Windows, WSL, containers, remote hosts, or network-mounted homes.

## Integrity

The version table (`bootstrap/versions.json` in agent-bun-runtime) lists each approved version with the SHA256 of every supported target's archive and the name of the single expected member. Adding a version means verifying Bun's `SHASUMS256.txt` against its GPG signature `SHASUMS256.txt.asc` with the release key whose fingerprint `bootstrap/README.md` records (done for 1.4.5 with GnuPG 2.4.7 and `--assert-signer`), then running the phase 1 scenarios. The starter never downloads `SHASUMS256.txt` at install time and never trusts a checksum fetched next to the archive.

The starter verifies the archive hash before unpacking, accepts only an archive holding exactly the expected member plus its parent directories, extracts that member by name to `bin/bun` (`bin\bun.exe`), and requires `bun --version` to equal the pin before publishing (scenarios 4, 5, 6; `getty-bun.ps1` probes once more after publishing, card `agent-bun-runtime k19`). Then it writes `receipt.json` into the stage. Its form is fixed in `bootstrap/README.md` ("Slot and receipt"): ASCII, LF, two-space indentation, the keys `version`, `target`, `archiveSha256`, `contractVersion`, `archive`, `member`, `binarySha256`, `executable`, `verifiedAt` in that order. The starters read only its first three lines (`{`, version, target, compared as whole strings); they do not read `executable` but take `bin/bun` (`bin\bun.exe`) in the slot. `executable`, the hashes and the timestamp are diagnostics for other readers, which parse the receipt as JSON and ignore unknown keys. A receipt records a verified operation; it does not prove that today's file is intact.

## Consumer binding

**Bundled entry (normal case):** the entry bundles `@getty/agent-bun-runtime`; no consumer lock and no machine-local binding (ADR 0003); `run` needs only the runtime slot. The committed pin block takes the binding's place: every starter call derives the slot from it, and the committed bundle is the only code that runs. A moved or updated plugin needs no rebind.

**Later/optional (plan phase 5, for a consumer that cannot bundle):** a frozen-lockfile dependency install on the user machine under a consumer lock, with a machine-local binding: consumer/content identity, package root, manifest and lockfile digests, runtime key, resolved absolute executable, receipt identity, dependency and smoke-test result. Publish it only after runtime and dependencies pass; reject a mismatch at execution instead of selecting another Bun. The runtime-key mutex does not protect a separate `node_modules` tree. See [dependencies-and-execution.md](dependencies-and-execution.md).

## Portability boundary

Distribute the same bundled TS/JS entry across supported targets without compiling a custom executable per OS. A compatible Bun binary from the table and the matching starter are still required. Shell commands, filesystem conventions, native add-ons (which rule out bundling), and host APIs remain platform-sensitive. Verify these boundaries rather than promising universal execution from a file extension.
