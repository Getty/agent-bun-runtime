# Paths and platform selection

Use [contract.md](contract.md) for ownership and canonical fields. Windows facts marked "measured by windows-developer" come from that hub (`docs/hook-start-windows.md`, `docs/starter-konvention.md`, `docs/umgebung.md`; Claude Code 2.1.287, Windows 11 25H2, PowerShell 5.1.26100). Facts marked executed come from agent-bun-runtime's CI on `windows-latest` (a server image, Defender real-time protection off); agent-bun-runtime `bootstrap/README.md` names the run per claim. Everything else on Windows is source-checked or not checked.

## Resolve the root once, then use absolute paths

`GETTY_HOME`, if set, is the root and must be absolute. Otherwise:

| Environment | Default root | Executable |
| --- | --- | --- |
| Linux, macOS (from 0.2.0, `getty-bun.sh`) | `~/.getty` | `<GETTY_HOME>/runtimes/bun/<version>/<target>/bin/bun` |
| Native Windows | user profile (`[Environment]::GetFolderPath('UserProfile')`) plus `\.getty` | `<GETTY_HOME>\runtimes\bun\<version>\<target>\bin\bun.exe` |
| Git Bash, MSYS, Cygwin | as native Windows: `getty-bun.sh` forwards to `getty-bun.ps1` | the same slot as native Windows |
| WSL | the distribution's Linux home | Linux layout and target; never a Windows `bun.exe` |
| Remote/container | the home of the user/environment actually executing the tool | that environment's OS layout |

On Windows, do not derive the root from `$HOME` or `$env:HOME`: Git Bash sets `HOME` to a `/c/Users/...` path. Tildes and angle-bracket names are notation. Never hardcode another machine's home path.

`GETTY_HOME` is one override for a whole environment (and for tests, which always set it), not a per-consumer setting. Two consumers seeing different `GETTY_HOME` values get separate stores and locks: safe, but not shared. `GETTY_BUN_MIRROR` changes only the download base URL; the pinned SHA256 still decides.

For a home shared between incompatible execution contexts (network homes, synchronized profiles), set `GETTY_HOME` to a local root per context first.

## Select a real release artifact

The target comes from the reviewed version table, never from a plausible asset name. Targets: `linux-x64`, `linux-x64-baseline` (no AVX2), `linux-aarch64`, `windows-x64`, `windows-x64-baseline`, and from 0.2.0 `darwin-x64` and `darwin-aarch64` (`getty-bun.sh`; executed, agent-bun-runtime CI 46035250753, the scenario legs on `macos-15-intel` and `macos-15` arm64; a Rosetta shell: not checked). musl and `windows-aarch64` come later as explicit table entries; until then the starter detects them and fails with a message naming the target.

Detection as built (agent-bun-runtime `bootstrap/README.md`):

- Linux: `uname -m` (`x86_64` -> `x64`, `aarch64`/`arm64` -> `aarch64`); `x64` without `avx2` in the first `flags` line of `/proc/cpuinfo` -> `x64-baseline`; unreadable -> baseline. A musl loader without the glibc one fails as `linux-<arch>-musl`. No fallback when an x64 Bun dies with SIGILL (card `agent-bun-runtime k12`).
- Windows: `PROCESSOR_ARCHITEW6432`, else `PROCESSOR_ARCHITECTURE` (`AMD64` -> `x64`; `ARM64` fails as `windows-aarch64`). AVX2 via `IsProcessorFeaturePresent(40)` through `Add-Type`, only when neither x64 slot exists: before an install, and in `status`, which then reports `missing` with the detected target; never for `run-ready`, whose "not installed yet" line names the first candidate, `windows-x64`, without detecting (`Add-Type` compiles, on every such hook); where `Add-Type` cannot load (Constrained Language Mode, no compiler) -> `x64-baseline`. The `Add-Type` check and the ARM64 failure (simulated through `PROCESSOR_ARCHITECTURE`): executed, agent-bun-runtime CI 45572032454. An x64 probe dying with `STATUS_ILLEGAL_INSTRUCTION` publishes nothing, and the starter installs `windows-x64-baseline` under that target's lock (source-checked, `getty-bun.ps1:692-709`; a local run with a fixture probe, not in CI; a real CPU without AVX2: not checked).
- Windows fast path: the first existing slot of `windows-x64`, then `windows-x64-baseline`, without CPU detection; a mismatching `windows-x64` slot fails closed and is never skipped (source-checked, `getty-bun.ps1:218-225`; executed, agent-bun-runtime CI 46035250753, the Windows PowerShell 5.1 and pwsh 7 legs, `bootstrap/test/fast-target.test.ts`, with planted slots). A profile that moves to a CPU without AVX2 keeps its x64 slot, and Bun dies there (not checked); removing that slot lets the next call install the baseline.

When adding a version, inspect the **chosen exact release**: OS, architecture of the process that executes Bun, libc/ABI, minimum OS, CPU instruction requirements and baseline variants, archive layout, expected member. Use official [Bun installation documentation](https://bun.sh/docs/installation) and [release assets](https://github.com/oven-sh/bun/releases). Treat emulation as an explicit tested target; do not reuse Windows executables in WSL or assume host runtimes exist in containers.

## Keep three paths separate

1. **Runtime executable:** `<GETTY_HOME>` plus the pin block.
2. **Consumer root:** derived by the starter from its own path, never from the working directory. `<entry>` is relative to it. This skill writes it `<consumer-root>`; in a hook command the host's placeholder stands for it: `${CLAUDE_PLUGIN_ROOT}` (Claude Code), `${PLUGIN_ROOT}` (Codex). Hosts start hooks in the session's working directory (Codex: documented), so the working directory says nothing about the plugin.
3. **User project:** explicit application input or the chosen working directory.

The bundled entry needs no module resolution at runtime. Pass project paths as arguments where supported.

## Quoting and process start

Prefer executable-plus-argument arrays. Quote for the actual shell when shell syntax is unavoidable; POSIX escaping is not PowerShell escaping. Test spaces, non-ASCII characters and separators in `GETTY_HOME` and in the consumer root (an old briefing bug was a non-ASCII home).

Windows rules for `getty-bun.ps1`, as built (agent-bun-runtime `bootstrap/README.md`, "Windows starter"):

- Invocation: `powershell.exe -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File "<consumer-root>\bootstrap\getty-bun.ps1" run <entry> [args]`. Cost: measured by windows-developer, a PowerShell start takes about 720 ms on a desktop; executed in agent-bun-runtime CI, the starter adds 348–522 ms over Bun alone, 171–294 ms of it the PowerShell start (medians, 5.1 and 7), a lower bound for desktops ([claude-code.md](claude-code.md), "Windows: the dot-sourced polyglot"). An execution policy set by Group Policy takes precedence over `-ExecutionPolicy Bypass` (documented for 5.1 and 7, [about_Execution_Policies](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies)); if that policy turns scripts off or is `AllSigned`, the unsigned starter cannot run (derived, not measured).
- Run Bun through `System.Diagnostics.Process` (`UseShellExecute = $false`, `CreateNoWindow`, stdin and stdout redirected, stderr inherited) and copy stdin and stdout as raw bytes asynchronously; close the child's stdin at end of input; end once Bun has ended, even while the host keeps stdin open; exit with the child's `ExitCode` (executed, scenarios 8 and 8b on 5.1 and 7). **Never run Bun with `&`**: measured by windows-developer (probe y4), Windows PowerShell 5.1 did not pass the end of stdin to a native program; the hook hung until its timeout and the process stayed behind. PowerShell's pipeline also re-encodes text. The cost of `CreateNoWindow`: Ctrl+C in the host's console does not reach Bun, and Bun survives a kill of `powershell.exe` (not checked; card `agent-bun-runtime k13`).
- 5.1 has only `ProcessStartInfo.Arguments`: quote every argument by the `CommandLineToArgvW` rules (spaces, embedded quotes, trailing backslashes, non-ASCII: executed, scenario 8).
- Entry arguments may begin with `-` (`-x`, `-x:foo`, `-x:`, `--`, `--%`, `-File`, `-Command`), with Windows exceptions. `-File` turns an argument that begins with `-` into a parameter, and binding can fail on one before the starter runs, with PowerShell's own message ("argument "name" is not valid") and exit 1, no `getty-bun: ` line; which ones fail depends on the version. So on Windows pass no lone `-` (Windows PowerShell 5.1, which the forwarding, the polyglot and `commandWindows` call, rejected it called directly both as the last argument and followed by another, pwsh 7 called directly passed both; `- x` also failed through the forwarding and through the polyglot from 5.1, pwsh 7 and Git Bash: executed, agent-bun-runtime CI 46035250753, `bootstrap/test/windows-dash-limit.test.ts`, `polyglot.test.ts`) and nothing that begins with `-:` (`-:foo` passed 5.1 called directly and was rejected by pwsh 7 called directly: executed, CI 46035250753); a lone last `-` and `-:foo` through the forwarding and the polyglot: not checked; a dash followed by nothing but blanks fails too (source-checked only, PowerShell v6.0.0 and master `CommandLineParameterParser.cs`). Through the polyglot from a PowerShell hook shell (5.1 and pwsh 7) also pass no `--%` and nothing that begins with `-` and contains a blank: `'--%'` did not arrive and `'-Command x'` arrived as `-Command` and `x`; Git Bash as hook shell passed both (executed, CI 46031834399 and 46035250753; that every such argument splits: derived from `-Command x`, the one run; `cmd.exe /d /c` running the `.cmd` was checked for stdin, stdout and exit code only, with no arguments; where PowerShell loses them: not checked). [contract.md](contract.md), "Entry arguments pass through unchanged (from 0.2.0)". An empty argument survives a `-File` call that a program builds (an exec form, Bun) and the Git Bash forwarding, but not a native call a PowerShell session writes: Windows PowerShell 5.1 drops it from every native command line, pwsh 7.3 and later from a `.cmd` call, so it is lost in the polyglot's hook line and in a Codex `commandWindows` line under 5.1 (documented for PowerShell, `about_Preference_Variables`; for the starter derived, not checked). `-File` hands the arguments after the script path to PowerShell's parameter binding, which re-parses those that begin with `-` before the script sees them (pwsh 7 splits `-x:foo` into `-x` and `foo` and drops `--%`). So `getty-bun.ps1` reads its arguments from the process's own argument vector, `[Environment]::GetCommandLineArgs()`, which that binding does not touch: the ones after the first `-File` (also `-f`, `-fi`, `-fil`; with `-`, `--` or `/`) whose next argument names a file with the running script's file name (source-checked, agent-bun-runtime `getty-bun.ps1:809`). A caller that quotes by the C runtime's rules (Bun, MSYS and the starter itself do) gets every argument back unchanged, the exceptions above aside. A starter started any other way (`&` inside another PowerShell session, pwsh's positional script without `-File`, a `-File` path written as an 8.3 short file name) falls back to `$args`, re-parsing included. Evidence: executed with pwsh 7.7.0 on Linux, not in CI: the starter (agent-bun-runtime `bootstrap/README.md`, "Entry arguments"), and its argument reader alone with `-File`, `-f`, `-fi` and `--file`, a script path with a space and `..` in it, and `&` inside `-Command` falling back; Windows PowerShell 5.1, pwsh on Windows, the Git Bash forwarding and the polyglot: executed, agent-bun-runtime CI 46031834399 and 46035250753 (`bootstrap/test/entry-args.test.ts`, `bootstrap/test/polyglot.test.ts`), with the exceptions above.
- Bun itself consumes one `--` that directly follows the entry: `bun <entry> --` gives the entry no argument, `bun <entry> -- x` gives `x`, while `bun <entry> x --` and `bun <entry> -- --` keep a `--` (executed, Bun 1.4.5 on Linux, raw, without a starter). The starters cannot change that: to hand an entry a leading `--`, write it twice. On Windows: the same Bun code, not checked (the Windows CI legs of `entry-args.test.ts` compare with a raw Bun).
- In a PowerShell command line (Codex's `commandWindows` in a PowerShell session, the polyglot's hook line), `--%` is PowerShell's stop-parsing token and never reaches the call: in `commandWindows` write `'--%'` (not checked on Windows); in the polyglot's hook line even `'--%'` was lost under PowerShell (above), so leave it out there.
- Language level 5.1: no `??`, `?.`, ternary, `&&`/`||` between commands, `$IsWindows`, `ProcessStartInfo.ArgumentList`. Keep the file pure ASCII with LF; 5.1 reads a file without BOM in the ANSI code page (checked by agent-bun-runtime's static CI job).
- Measured by windows-developer: Claude Code sends UTF-8 JSON on stdin with backslash paths inside and passes stdout through unchanged.

Git Bash, MSYS2 and Cygwin forwarding, as built: `getty-bun.sh` hands every call to the `getty-bun.ps1` next to it, preferring Windows PowerShell 5.1 by its fixed path under `$SYSTEMROOT`, converts a POSIX `GETTY_HOME` with `cygpath -w`, and sets `MSYS_NO_PATHCONV=1` and `MSYS2_ARG_CONV_EXCL='*'`, which stay in the entry's environment. Shared slot and lock: executed, scenario 11; the converted `GETTY_HOME` and unchanged arguments: executed, agent-bun-runtime CI 45589361806; the 5.1 preference: source-checked. Exit codes 0, 1, 2, 7 and 42 come back unchanged (executed, agent-bun-runtime CI 45579886904); a crash's NTSTATUS maps differently per path (source-checked; `bootstrap/README.md`, "Limit: exit codes through Git Bash").

Hint for hosts and tests, not a requirement: give the starter its input on a pipe. Under Git Bash, a native PowerShell blocks reading an inherited NUL handle (executed, agent-bun-runtime CI 45589361806), so for a stdin that is a character device but no terminal (`/dev/null`) the forwarding starts PowerShell on an empty pipe instead of `exec` (executed, CI 45597390051). On that path a signal to the shell ends only the shell (card `k13`). Hook input on a pipe keeps the `exec` path; that hosts use a pipe is inferred for Claude Code (windows-developer recorded the JSON and end of input, not the handle type) and not measured for Codex.

### The polyglot `getty-bun.cmd` on Windows

A Claude Code hook that must start on Linux, macOS and Windows alike uses shell form and dot-sources `<consumer-root>/bootstrap/getty-bun.cmd` (agent-bun-runtime ADR 0010; the line and its JSON: [claude-code.md](claude-code.md) and skill `getty-bun-install`). On Windows without Git Bash the line runs under PowerShell:

```
. "${CLAUDE_PLUGIN_ROOT}/bootstrap/getty-bun.cmd" run dist/hook.js; exit $LASTEXITCODE
```

What a consumer needs on Windows (source-checked against agent-bun-runtime `bootstrap/getty-bun.cmd` unless labelled otherwise):

- **What runs.** PowerShell's `.` runs a `.cmd` as a native command, through `cmd.exe`. `cmd.exe` skips the first line (a label to it) and runs, with `@echo off`, `"%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe" -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File "%~dp0getty-bun.ps1" %*`, then `exit /b %ERRORLEVEL%` (`getty-bun.cmd:9-10`). `%~dp0` is the polyglot's own directory, `%*` the arguments as `cmd.exe` received them; `getty-bun.ps1` then reads them from its process command line (above). stdin, stdout and stderr are inherited, nothing else writes to stdout, the exit code is the starter's. The file holds no pin; it must sit next to `getty-bun.sh` and `getty-bun.ps1`, which it calls. Under Git Bash, Linux and macOS the same line sources the file as shell code, which hands the call to `getty-bun.sh` (and from Git Bash on to `getty-bun.ps1`).
- **The cost.** A hook through the polyglot on Windows starts the hook's own PowerShell, `cmd.exe` and Windows PowerShell 5.1 before Bun: one PowerShell start more than Codex's `commandWindows`, which calls `getty-bun.ps1` directly. On a desktop: not measured yet (a windows-developer card).
- **`; exit $LASTEXITCODE`.** PowerShell's `-Command` turns any non-zero exit code of a native last command into 1 (documented; executed with pwsh 7.7.0 on Linux by agent-bun-runtime, not on Windows); the tail hands the starter's code on, which Claude Code's exit 2 needs. A POSIX shell never reaches it: the polyglot ends the shell by `exec` or `exit`.
- **The polyglot call comes first in the line, nothing before it.** Its dash fallback on Linux reads the shell's command line and runs it again under bash; it does so only when the line starts with `. ` and the word after the dot names `getty-bun.cmd`, and otherwise fails with one `getty-bun: ` line and exit 1, since whatever came first would run twice. A command substitution inside the line (`$(...)`, backticks) does run twice under dash, once in dash and once in bash: keep them out (agent-bun-runtime `bootstrap/README.md`, "Polyglot"; executed locally with dash 0.5.12 and a stub starter, not in CI).
- **Absolute `powershell.exe`.** `cmd.exe` looks for a bare command name in the current directory before `PATH`, and a hook's current directory is the user's project; so the polyglot names Windows PowerShell 5.1 by its path under `%SystemRoot%`, never `pwsh` and never one found by name. Under a 32-bit `cmd.exe` that path reaches the 32-bit PowerShell (WOW64 file-system redirection, documented by Microsoft); `getty-bun.ps1` then reads the machine's architecture from `PROCESSOR_ARCHITEW6432` (source-checked; a 32-bit host on Windows: not checked). An environment without `SystemRoot` makes the path wrong, and `cmd.exe` fails with its own message, not a `getty-bun: ` line (not checked).
- **Metacharacters.** An argument written in the hook line passes three parsers on Windows: PowerShell reads the line, writes the arguments onto `cmd.exe`'s command line, and `cmd.exe` reads them again before `%*`. PowerShell passes arguments to a batch file in its legacy mode: an embedded `"` is not escaped and an empty string is dropped (documented, `about_Parsing`, `$PSNativeCommandArgumentPassing`; Windows PowerShell 5.1 has only that mode). `cmd.exe` expands `%name%`, takes `^` as its escape and `&`, `|`, `<`, `>` outside double quotes as operators, and expands `!name!` when delayed expansion is on in the registry (documented, `cmd /?`; through the polyglot: not checked). So the arguments in a polyglot line are words of letters, digits and `. _ - / : = , +`, single-quoted where PowerShell would read them otherwise (`'-x:foo'`); no `"`, no empty string, none of `% ^ & | < > !`, no `--%` and no `-` argument with a blank in it (both lost under a PowerShell hook shell, above). Host data travels on stdin, never as an argument, so the rule binds only what the plugin author writes. A consumer root containing `%`, `^`, `&` or `!` (a Windows user name may): not checked.
- **LF line endings, and why that is safe here.** The file is pure ASCII with LF line endings, as both POSIX sides need (a CR would end up in the shell's words). `cmd.exe` reads an LF-only batch file line by line; what is unreliable there is its label search (`goto`, `call :label`) and parenthesised blocks, and the batch part has none of them; `cmd.exe` stops at `exit /b` before the POSIX part. Keep it LF in the consumer's repository: `.gitattributes` with `* text=auto eol=lf` (below) overrides a Windows `core.autocrlf=true`; a polyglot checked out with CRLF breaks the POSIX side (how: not checked).
- **The missing-`.cmd` limit.** When PowerShell cannot find the polyglot (a wrong or unsubstituted root, a file not shipped), it writes its error to stderr, `$LASTEXITCODE` stays unset and `exit $LASTEXITCODE` exits 0: the hook passes without running, and a blocking hook blocks nothing (derived from PowerShell's semantics; not checked on Windows). A doctor or test that runs the line on Windows is the guard. A missing `getty-bun.ps1` next to it ends with PowerShell's own `-File` error and a non-zero exit code, not a `getty-bun: ` line (not checked).
- **`${CLAUDE_PLUGIN_ROOT}`.** If Claude Code did not substitute it before PowerShell parses the line, PowerShell would read it as its own, empty variable and look for `/bootstrap/getty-bun.cmd` (the limit above). Whether it substitutes: not checked (a windows-developer card).
- **Other `cmd.exe` limits, all not checked on Windows** (agent-bun-runtime `bootstrap/README.md`, "Limits of the batch side"):
  - *AutoRun* (derived from `cmd /?`): PowerShell starts the batch file as `cmd.exe /c` without `/d`, so a `Command Processor\AutoRun` command from the registry (`conda init` writes one) runs first; its output can land on the hook's stdout ahead of the hook JSON, and a `cd` in it changes the directory the starter and the entry start in.
  - *UNC working directory* (derived from `cmd.exe`'s documented behavior): a project on a network share is not supported as `cmd.exe`'s current directory; it warns and runs in the Windows directory, so the entry's `location.processCwd` is `C:\Windows`, not the project.
  - *`SystemRoot` unset* (derived): the PowerShell path stays literal `%SystemRoot%\...`, `cmd.exe` fails with its own message, not a `getty-bun: ` line, and a non-zero exit code.
  - *`$` or a backtick in the plugin root* (derived from PowerShell's double-quoted string rules): PowerShell expands them inside the line's double quotes, finds no polyglot and the line exits 0, as in the missing-`.cmd` limit above: the hook fails open.
  - Ctrl+C may raise `cmd.exe`'s "Terminate batch job" prompt (card `agent-bun-runtime k13`).
- **Evidence.** windows-developer measured a dot-sourced `.cmd` polyglot in shell form starting under Claude Code 2.1.287 (probe q6, `docs/hook-start-windows.md` there), not this file. This file on Windows: executed, agent-bun-runtime CI 46035250753, the Windows PowerShell 5.1 and pwsh 7 legs of `bootstrap/test/polyglot.test.ts`, dot-sourced from Windows PowerShell 5.1, pwsh 7 and Git Bash (also with a backslash root): stdin and stdout byte for byte with exit 7, the dash arguments (the PowerShell exceptions above), a run without `CLAUDE_PLUGIN_ROOT`, a starter failure as exit 1; `cmd.exe /d /c` on the `.cmd`: bytes and exit 7, no arguments. Not checked on Windows: exit 2 through the `; exit $LASTEXITCODE` tail, a host that keeps stdin open through the polyglot, an argument list given to `cmd.exe` directly. Its POSIX side: executed on Linux with sh, dash, bash, BusyBox sh and zsh, and on macOS (CI 46035250753) with `/bin/sh`, `/bin/bash` 3.2 and zsh, dash failing there as documented (agent-bun-runtime `bootstrap/README.md`, "Polyglot"). MCP servers have no shell form: the polyglot does not start them.

Repository hygiene for consumers that ship starters: `.gitattributes` with `* text=auto eol=lf`, plus `*.exe binary` if the consumer ships a Windows executable (the shim option in [claude-code.md](claude-code.md); windows-developer `docs/starter-konvention.md`); no checked-in symlinks (measured by windows-developer: they become text files without developer mode).

## Host lifecycle

Claude Code uses versioned plugin cache locations; its plugin data has a separate lifecycle and may be removed on uninstall. Keep the store outside both. Source: [Claude Code loading](https://code.claude.com/docs/en/plugins/loading). Codex exposes the installed plugin root as `PLUGIN_ROOT` and, for compatibility, `CLAUDE_PLUGIN_ROOT` to plugin hook commands (documented, not executed) and substitutes `${PLUGIN_ROOT}` textually into the command string before the shell runs it (source-checked, openai/codex `3f65e9f`, not executed); quote it ([codex.md](codex.md)).

A moved or updated plugin needs nothing beyond its committed starters and bundle: the starter derives the consumer root afresh on every call, and the shared runtime remains valid.
